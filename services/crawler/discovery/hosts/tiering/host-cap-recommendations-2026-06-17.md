## 4. Path-Pattern Suggestions

The following additional `path_patterns` regexes are recommended for `host-blocklist.yaml`,
beyond the ones already added (`/playlists?/`, `/track/`, `/tracks/`, `/calendar/`,
`/events?/\d`, `\?page=\d`, `\?p=\d`, `/search\b`, `/tag/`, `/tagged/`, `/archive/\d`).

```yaml
# Job board / listing traps
- /jobs/\d          # dynamic job listing pages (jobs.vt.edu, jobs.apply.vt.edu)
- /listing/\d
- /position/\d

# News archive pagination (supplement ?page= for path-based paging)
- /news/\d{4}/      # e.g. /news/2019/05/story — year-keyed archive paths
- /press-release/\d

# Event archive traps (supplement /events?/\d)
- /event/\d{4}-\d{2}-\d{2}/  # date-keyed event paths
- /events/\d{4}/

# WordPress media/asset upload paths
- /wp-content/uploads/
- /wp-json/

# Course catalog / registration dynamic paths
- /class-schedule/
- /timetable/

# Giving/donation transactional flows
- /give/
- /donate/
- /gift/

# Crowdfunding project listings
- /projects?/\d
- /campaign/\d

# Playlist/media archive (extend beyond wuvt)
- /playlist/\d
- /episode/\d
- /podcast/\d

# Feed/RSS traps
- /feed/?$
- /rss/?$
- /atom/?$

# WordPress backend origin pattern (catch all *.wp.prod.es.cloud.vt.edu)
# Add to patterns: section as regex:
- \.wp\.prod\.es\.cloud\.vt\.edu$
```

**Priority additions** (highest firehose risk):
1. `\.wp\.prod\.es\.cloud\.vt\.edu$` — catch all WordPress backend origins in one pattern (currently `agpestadvisoryvaes.wp.prod.es.cloud.vt.edu` is in the registry; this pattern would catch any newly-discovered ones)
2. `/wp-content/uploads/` — prevents crawling binary upload trees on any WordPress host
3. `/news/\d{4}/` — supplements `?page=` for archive-style news paths (vtnews, eng news, etc.)
4. `/jobs/\d` — dynamic job listing pages
5. `/feed/?$` + `/rss/?$` — RSS/Atom feed endpoints return XML, not HTML prose

## Appendix: Decision Rationale for Major Tiers

**Why BLOCK redirect aliases?** When a host at -1 is a pure 301 redirect to another host
already in the registry at -1, the crawler will follow the redirect and index the target.
The source host just adds a duplicate seed URL. Blocking it keeps the registry clean.

**Why 1 for lab micro-sites?** Faculty/lab sites (e.g. `collinslab.bme.vt.edu`,
`wanglab.beam.vt.edu`) typically have: an index page with people/publications, a few
sub-pages for projects, and then deep per-paper or per-person pages. The index page captures
what a student needs ("what does this lab do?"). Unlimited crawl would mostly pull CVs and
publication PDFs already indexed via vtechworks.

**Why 25 for news/events?** The goal is a representative sample for RAG — enough to answer
"what's new in X department?" without ingesting years of press releases. 25 pages covers
~1-3 months of news for active departments.

**Why keep -1 for service offices?** Offices like HR, Financial Aid, Registrar, and Housing
have deep policy/FAQ trees that students query frequently ("what are the FAFSA deadlines?",
"how do I apply for housing?"). Unlimited crawl on these is intentional.
